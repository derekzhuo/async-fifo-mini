# 04 综合与结果解读：面积趋势、拓扑路径与时序边界

功能仿真回答「逻辑行为是否符合预期」，综合则把 RTL 展开成具体逻辑网络，帮助观察资源规模和结构趋势。本工程使用 Yosys 的通用 `synth` 流程，不绑定任何 FPGA 或 ASIC 标准单元库。因此它能提供有意义的相对比较，却不能替代目标器件的布局布线和静态时序分析。

这一篇先说明命令和产物，再用同一次工具链生成的七组数据讨论深度、位宽和总容量之间的关系。

## 一、单档综合：`make syn`

在仓库根目录运行：

```bash
make syn
```

该目标执行：

```bash
yosys -s scripts/syn.ys
```

脚本内容按顺序为：

```tcl
read_verilog rtl/async_fifo.v
hierarchy -top async_fifo
synth -top async_fifo
stat
sta
```

各步骤的作用如下：

| 命令 | 作用 |
|---|---|
| `read_verilog` | 读入 RTL，使用默认 `DATA_WIDTH=8`、`ADDR_WIDTH=4` |
| `hierarchy` | 确立 `async_fifo` 为顶层并解析层次 |
| `synth` | 执行通用综合、优化与工艺无关单元映射 |
| `stat` | 输出线网、寄存器和单元数量等统计 |
| `sta` | 尝试静态时序分析；当前通用单元没有可用时延模型，因此不会得到有效纳秒路径 |

`make syn` 适合确认 RTL 可综合、查看默认参数的资源统计。它的 `sta` 输出不应被解读为「已经通过 100 MHz」或「没有时序问题」。

## 二、参数矩阵：`make matrix`

运行：

```bash
make matrix
```

实际入口是：

```bash
bash scripts/run_matrix.sh build/matrix
```

脚本遍历 `ADDR_WIDTH = 2、4、6` 与 `DATA_WIDTH = 8、32`，即默认六档：

| 深度 | 位宽 | 数据存储容量 |
|---:|---:|---:|
| 4 | 8 | 32 bit |
| 4 | 32 | 128 bit |
| 16 | 8 | 128 bit |
| 16 | 32 | 512 bit |
| 64 | 8 | 512 bit |
| 64 | 32 | 2048 bit |

每一档都重新执行读入、参数覆盖、综合、`stat`、`ltp` 和 `sta`。核心命令形态是：

```bash
yosys -p "read_verilog rtl/async_fifo.v; \
chparam -set DATA_WIDTH 32 -set ADDR_WIDTH 4 async_fifo; \
hierarchy -top async_fifo; synth -top async_fifo; stat; ltp; sta"
```

这里 `ltp` 报告最长拓扑路径，用于观察路径经过多少级逻辑。脚本把结果写进：

```text
build/matrix/
├── matrix-summary.log
├── depth-4-width-8.log
├── depth-4-width-32.log
├── depth-16-width-8.log
├── depth-16-width-32.log
├── depth-64-width-8.log
└── depth-64-width-32.log
```

汇总表方便横向比较，单档日志保留完整综合过程。需要换输出目录时可执行：

```bash
make matrix MATRIX_DIR=build/my-matrix
```

### 第七档 `16×128` 从哪里来

本文数据表还包括深度 16、位宽 128 的一组追加实验。它不是当前 `run_matrix.sh` 的双重循环默认产物，而是用同一综合命令额外覆盖 `DATA_WIDTH=128`、`ADDR_WIDTH=4` 得到的结果，用于与 `64×32` 比较相同 2048 bit 总容量下的结构差异。因此，直接重跑 `make matrix` 应预期六行，不要因为汇总目录中少第七行而认为运行失败。

## 三、七组真实结果

以下数字全部来自 Icarus Verilog 13.0 / Yosys 0.33（`geek-eda:0.2` 容器）于 2026-10-30 的通用综合记录。`cells` 是 Yosys 映射后的通用单元总数，`critical_path_ltp_levels` 是最长拓扑路径级数。

| 深度 | 位宽 | 数据容量（bit） | cells | longest_path_ns | slack_ns | 最长拓扑路径（级） |
|---:|---:|---:|---:|---|---|---:|
| 4 | 8 | 32 | 156 | NA | NA | 37 |
| 4 | 32 | 128 | 396 | NA | NA | 34 |
| 16 | 8 | 128 | 555 | NA | NA | 54 |
| 16 | 32 | 512 | 1661 | NA | NA | 54 |
| 64 | 8 | 512 | 1985 | NA | NA | 72 |
| 64 | 32 | 2048 | 6547 | NA | NA | 72 |
| 16 | 128 | 2048 | 6077 | NA | NA | 45 |

`NA` 是数据结论的一部分，不是缺表后随便补的空位：当前流程无法给出可信的纳秒延迟与 slack，不能用拓扑级数乘一个假设门延迟来伪装成时序结果。

## 四、为什么 generic 流程给不出纳秒 slack

`sta` 要计算路径延迟，至少需要每类单元的时延模型、输入转换与输出负载等信息；真实 FPGA 还依赖具体 slice、布线资源、速度和温度等级。通用 `synth` 生成的是工艺无关逻辑单元，脚本也明确记录：

```text
sta: generic synth cells are unrecognized, so delay/slack are NA; ltp supplies topological path levels
```

单档日志里会出现：

```text
No timing paths found
```

这并不表示设计中不存在组合路径，更不表示时序无限好，而是当前 STA 上下文无法识别可用于时延计算的路径模型。矩阵脚本据此把 `longest_path_ns` 与 `slack_ns` 写成 `NA`，只保留拓扑路径级数。

脚本头虽然描述目标 100 MHz、周期 10 ns，以及「有延迟时 slack = 10 ns - 路径延迟」的计算方式，但这次所有档都没有可用延迟，所以 **100 MHz 不是已经验证的频率**。把任何一档写成「slack 很大」「轻松过 100 MHz」都没有数据依据。

## 五、面积随深度和位宽近似线性增长

先看固定位宽、增加深度：

- 8 位宽：4 深 156 cells，16 深 555 cells，64 深 1985 cells；
- 32 位宽：4 深 396 cells，16 深 1661 cells，64 深 6547 cells。

深度每扩大 4 倍，单元数大致也接近 4 倍。再看固定位深、增加位宽：16 深从 8 位到 32 位，555 增至 1661，接近 3 倍；64 深同变化为 1985 到 6547，约 3.3 倍。不是严格 4 倍，因为地址指针、同步器、满空比较等控制逻辑不随 `DATA_WIDTH` 等比例增长，优化与映射也会改变单元组成。

这些结果符合当前存储结构：数据项越多、每项越宽，存储元件和组合读选择网络越大。不能把 `cells` 当成门数、LUT 数或平方微米，它最适合回答「同一工具、同一 RTL、不同参数怎样变化」。

## 六、关键路径随深度增长，位宽不是主要推动因素

8 位数据时，深度从 4、16 到 64，最长拓扑路径从 37、54 增至 72 级；32 位数据在 16 深与 64 深也分别为 54、72 级。这个趋势与组合读结构吻合：

```verilog
assign rdata = mem[rbin[ADDR_WIDTH-1:0]];
```

深度增加意味着更大的读多路选择网络和更复杂的地址译码，数据从存储到 `rdata` 要经过更多逻辑层。另一方面，位宽增加通常让更多数据位并行复制相似路径，并不必然串联更多级：16 深从 8 位到 32 位都是 54 级，64 深两者都是 72 级。

4 深是 37 级对 34 级，位宽增大反而略少，说明通用映射和优化会改变局部结构，不能把「位宽完全不影响级数」说成绝对定律。可靠结论是：**本组数据中，深度增加带来明显的级数增长，而位宽增加没有表现出持续、单调的级数增长。**

`16×128` 为 45 级，也提醒我们不要仅凭一个参数公式推测所有映射结果。数据宽度、存储形状和优化策略会共同改变网络。

## 七、同样 2048 bit，为什么 `16×128` 与 `64×32` 不同

两组配置的数据存储容量相同：

```text
16 × 128 = 2048 bit
64 × 32  = 2048 bit
```

但单元数为 6077 与 6547，规模接近但并不相等；最长拓扑路径差异明显，分别为 45 与 72 级。这说明「总 bit 数相同」不等于「硬件结构相同」。

- `64×32` 有更多地址项，读选择需要在 64 项之间选择，地址更宽、选择网络更深；
- `16×128` 只有 16 项，但每项更宽，更多逻辑沿数据位并行展开；
- 指针和同步器宽度也不同：前者 `ADDR_WIDTH=6`，后者为 4；
- 综合器可能采用不同的单元分解与共享优化，因此面积不能只按总存储位数推断。

选型含义是：如果协议允许自由选择「更深更窄」或「更浅更宽」，不能只看总容量。浅而宽在这组通用综合中表现出更短的读选择路径，面积也略小；但真实器件还要考虑总线位宽、布线拥塞、RAM 宏形状和接口吞吐，最终结论应来自目标流程。

## 八、要上板或要真实 slack，应转到厂商流程

要回答某款 FPGA 上能否跑到目标频率，应把设计带入对应工具链，例如 Xilinx/AMD Vivado 或 Intel Quartus，并完成以下工作：

1. 选择准确器件、封装和速度等级，使用厂商综合与布局布线；
2. 为 `wclk`、`rclk` 分别创建时钟，不把异步关系误写成同一时钟；
3. 对跨域同步路径设置合适约束，并确认同步寄存器被识别、保留和合理布局；
4. 检查 CDC 报告、复位释放、多时钟路径和未约束路径；
5. 查看实际 LUT、FF、分布式 RAM 或 BRAM 使用，而不是把通用 `cells` 直接换算过去；
6. 根据实现后的 STA 报告评估最坏情况 slack，必要时修改存储读结构或采用厂商双时钟 FIFO IP。

尤其要记住当前 RTL 的组合读往往不利于典型 BRAM 推断。若为了 BRAM 改成同步读，读数据时序会变化，testbench 与上游接口也必须同步调整。厂商 IP 还会提供水位、计数、复位与 CDC 约束等完整配套，适合产品化，但不应掩盖本教程所解释的底层机制。

通用综合的正确用途是尽早发现不可综合写法、观察参数趋势和比较结构；真正的频率签核必须落在目标器件与实现结果上。
